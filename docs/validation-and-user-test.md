## 2. Dev 联调清单

### Dev 1：合约

- 提供已部署的合约地址、ABI、每个测试交易 Hash。
- 说明每一个事件的字段及其人类含义。
- 提供正常履约、自动赔付、安全失败三种可重复测试参数。
- 确认 `actualOutput` 由用户余额变化测量，且外部调用失败后退款/补偿不会整体回滚。

### Dev 2：前端

- 每个显示金额都按代币实际 decimals 格式化。
- 页面从真实合约事件读取已上链计划和结算结果。
- 演示状态与真实 Testnet 状态在视觉上明确区分。
- 支持复制 Hash、打开 Explorer、处理拒签、网络错误、过期和交易失败。

### Research 验收

- 对照 `product-spec.md` 的六个测试场景逐项签字。
- 核对前端每一句核心文案是否与事件和合约行为一致。
- 对每个真实案例保存 Explorer、截图和一句普通语言解释。

## 3. 三人用户理解测试

### 招募对象

3 名非团队成员；至少 1 名 Web3 新手。使用测试钱包和测试资产，不要求真实资金。

### 流程

1. 让参与者自行浏览报价页和担保计划，不进行讲解。
2. 让其用自己的话回答下方问题。
3. 让其指出“保证输出”“保证金”“失败补偿”和“MockDex”分别在哪里。
4. 记录犹豫、误点、阅读跳过和原话。

### 必答问题

1. 谁提供了保证金？
2. 这个产品保证的是什么，不保证什么？
3. 如果实际到账低于保证输出，会发生什么？
4. 如果价格跌得超过赔付上限，会发生什么？
5. 这是实时 DEX 价格还是演示市场？

### 最小成功标准

- 3 人中至少 2 人无需提示即可正确回答前 3 题。
- 没有人把“保证输出”理解为“保证赚钱”。
- 没有人认为页面中的 MockDex 是实时真实市场。
- 根据反馈完成至少 3 项具体 UI/文案修改。

## 4. Demo Day 三分钟证据顺序

1. 用一句话说清：Agent 不只解释结果，也为可测量的结果锁定责任。
2. 输入 `1 MON`，展示预期输出、保证输出、最高赔付与 MockDex 披露。
3. 展示真实 `PlanOpened` 交易与锁定保证金。
4. 展示一次正常履约。
5. 改变 MockDex 汇率，展示一次自动补足差额。
6. 展示超出保障范围时的安全失败、退款与失败补偿。
7. 打开区块浏览器，最后明确：不保证盈利，不使用管理员或 LLM 决定是否违约。

## 5. 不允许的表述

- “AI 保证交易成功”
- “保险池”或“正式保险产品”
- “真实实时汇率”，除非接入真实 DEX 与可验证报价来源
- “已保护用户资产”，除非对应的 Testnet 流程和链上证据真实存在
- “已接入 Moss”，除非真实调用 Moss 并能在 Demo 中展示
